# 2026-07-02：VLN-CE / NeuPAN 文献对齐与后续优化方向

## 背景

组会反馈指出，当前系统不应把“原地转圈识别”和视觉命中后的推测式重定位作为主线方法。项目方向应靠近 VLN-CE：语言模块负责把 instruction grounding 到导航目标或候选航点，连续环境中的定位、规划、控制、恢复和到达状态应交给 Nav2/RViz 暴露，而不是由 bridge 额外插入识别式 oracle。

本次只整理优化方向和文献对齐，不修改 README，不修改主线代码。

## 阅读来源

- VLN-CE repo: https://github.com/jacobkrantz/VLN-CE
- VLN-CE paper: Krantz et al., "Beyond the Nav-Graph: Vision-and-Language Navigation in Continuous Environments", ECCV 2020, https://arxiv.org/abs/2004.02857
- VLN-CE waypoint paper: "Waypoint Models for Instruction-guided Navigation in Continuous Environments", https://arxiv.org/abs/2110.02207
- NeuPAN repo: https://github.com/hanruihua/NeuPAN
- NeuPAN paper/repo positioning: real-time, map-free, MPC-based local motion planning from obstacle points to control actions.

## VLN-CE 对当前项目的启发

VLN-CE 的核心不是“在原地看见目标”，而是把 VLN 从离散 nav-graph 推向连续环境执行。它要避免图导航中三个隐藏假设：

- 已知环境拓扑；
- oracle short-range navigation；
- perfect localization。

映射到本项目：

- 不应把 bridge 中的原地 360-degree scan 当作主线识别能力；
- 不应把 visual-anchor AMCL reanchor 当作主线定位能力；
- 应让 Nav2/RViz 暴露真实连续导航问题：规划失败、局部控制卡住、AMCL 漂移、costmap 障碍、到达误差和超时。

## NeuPAN 对当前项目的启发

NeuPAN 不是 VLN 识别方法，而是局部运动规划/避障参考。它的价值在于强调把局部运动控制作为 planner/controller 问题处理，输入 obstacle points，输出控制动作。

当前项目不需要马上替换 Nav2。更合理的顺序是：

1. 保留 Nav2 作为主线导航执行层；
2. 将 bridge 限制为 language grounding / goal selection；
3. 用 RViz 和日志评估 Nav2 的真实行为；
4. 如果后续要引入 NeuPAN，应作为 local planner / controller 对照实验，而不是替代 VLN 模块。

## 建议优化路线

### Step 1：先冻结主线任务定义

主线定义改为：

```text
instruction -> semantic goal / waypoint -> Nav2 NavigateToPose -> RViz + logged continuous metrics
```

视觉扫描、active search、visual-anchor reanchor 保留为 diagnostic/ablation，不写成 primary method。

### Step 2：重新定义指标

建议后续 CSV 至少记录：

- TL / path length；
- NE / final navigation error；
- SR / physical arrival within radius；
- SPL-style efficiency；
- timeout / stuck / recovery count；
- AMCL vs raw odom disagreement；
- Nav2 result；
- final pose source。

历史 strict visual success 可以保留，但应作为“visual confirmation ablation”，不是 VLN-CE 主指标。

### Step 3：优化目标生成，而不是优化原地识别

保留 `TextToPoseConverter`，但把目标从 object center 改为更稳定的 observation waypoint / semantic waypoint。优化重点：

- 每个语义目标维护一个或多个候选 observation poses；
- 用 occupancy map / costmap 检查候选是否 free；
- 用与目标的朝向关系选择 yaw；
- 对长距离目标先走可达 waypoint，再让 Nav2 完成局部接近。

### Step 4：让 RViz 成为调试入口

每次实验必须在 RViz 同时看：

- `/vln_goal_pose`；
- global plan；
- local costmap；
- `/scan`；
- AMCL pose；
- robot footprint；
- executed trajectory。

这样失败能分成 grounding 错误、goal 不可达、global plan 错误、local controller 卡住、localization drift，而不是笼统归因给 VLM。

### Step 5：做三个 ablation

建议下一轮只跑小规模、可解释 ablation：

1. `Nav2-only goal execution`：不用视觉扫描，只测 goal 到达能力；
2. `semantic waypoint selection`：object center vs observation pose vs multi-waypoint；
3. `local planner comparison`：Nav2 RPP baseline vs 后续 NeuPAN-style local planner（如果接入）。

## 当前结论

下一阶段不应继续围绕“原地转圈识别”修补。更强的论文叙事是：本项目是一个 ROS 2/Isaac Sim 中的 VLN-CE 实现，贡献在于把语言 grounding、Nav2 连续执行、定位模式分析和 RViz 可解释调试放在一个统一实验框架里。

### Isaac Sim focused chair rerun

为避免上一轮手动中断导致结果不完整，本轮先补强 subset runner：

- 新增 `--trial-ids`，可只跑指定 trial。
- 新增 `--stuck-timeout-sec` 和 `--stuck-min-progress-m`，让脚本在没有实质进展时自动 cancel 并写入 CSV。
- `finally` 中 cancel Nav2 task，避免测试退出后继续残留目标。

在 Isaac Sim 当前状态下，机器人 odom 约为：

```text
x=-0.269, y=-2.428, yaw≈2.116 rad
```

Nav2 / RViz 重新启动，`/scan`、AMCL、planner、controller、bt_navigator 均可用。AMCL 初始位姿设置到当前模拟位姿附近：


结果：

| Trial | Target | Policy | Result | Duration | Trajectory length | Final pose | Final error |
|---:|---|---|---|---:|---:|---|---:|
| 3 | chair | observation_pose | stuck | 47.195 s | 0.001 m | `(-0.269, -2.428, 2.116)` | 1.800 m |
| 3 | chair | object_center | stuck | 45.133 s | 0.001 m | `(-0.269, -2.428, 2.116)` | 1.759 m |

解释：

- `observation_pose` 和 `object_center` 在静态 map preflight 中均为 `goal_safe=True`。
- 两个目标策略都没有产生有效位移，轨迹长度只有 `0.001 m`。
- 因此当前 chair blocker 不是“目标点语义识别错了”这一层的问题，而是 Nav2 目标发送后局部执行/底盘控制链路没有推动机器人离开当前位姿。
- 这进一步支持架构调整：先把连续导航执行层调通，再谈 VLN grounding 或视觉扫描；原地转圈识别不应作为主线优化目标。

下一步优先级：

1. 检查 `/cmd_vel_nav` 到 `/cmd_vel` mux / teleop priority / Isaac Sim controller 接收链路，确认 Nav2 非零速度是否被覆盖成零。
2. 在 RViz 看 local costmap 是否把当前位姿附近全部判为障碍，导致 controller 只发布零速度或立即进入 progress failure。
3. 用一个更近的安全目标做 smoke test，例如从当前 `(-0.269, -2.428)` 到 `(-0.269, -2.0)`，隔离“目标点设计”与“底盘控制链路”。
4. 若近距离 smoke test 仍不动，优先修 ROS/Isaac velocity bridge；若近距离可动，再重设 chair observation waypoint 或加入中间 waypoint。

修正后的判断：

- 之前 chair stuck 不能再简单归因于速度桥或底盘不动；重启 Isaac 后，底盘和 Nav2 执行链路能移动。
- `chair object_center` 能在 `0.35 m` 半径内到达，说明 chair 语义目标本身可导航。
- `chair observation_pose` 仍然失败，并且会把机器人带到目标右侧偏远位置。这说明当前 observation pose `(0.20, -0.69, pi)` 或对应 local path 不适合当前地图/障碍布局。
